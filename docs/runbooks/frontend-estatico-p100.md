## Artefactos y contratos

El build debe tomar una fuente Git limpia en el SHA exacto, archivada fuera del checkout, usar el lockfile con `npm ci` y comparar dos builds. El release debe contener `dist/` y un manifiesto de sourceSHA, lockfile, versiones reales e inventario SHA256. La configuración implícita VITE_ y archivos env deben rechazarse; la hora va en el recibo del sistema, no cambia los bytes reproducibles. Reutilizar el mismo SHA con otros bytes debe fallar cerrado; R1 todavía no cumplía esta condición.

Nginx debe usar una instancia independiente bajo la misma unidad frontend y un drop-in gestionado único. El renderer debe derivar el contrato de los proxies de Vite: prefijos `/api` y `/ws`, ruta/query sin reescribir, Host del destino por changeOrigin y Origin conservado. No añade cabeceras de confianza X-Forwarded que Vite no emite. API y WebSocket nunca reciben el fallback HTML. El body grande conserva la capacidad actual del proxy.

`index.html` y las rutas SPA usan no-cache; los assets con hash usan caché immutable de31536000s. Los assets inexistentes responden404 sin HTML; los assets anteriores permanecen en un pool por nombre/hash sin GC durante aplicación o reversión. Un mismo nombre con bytes distintos aborta. El SHA del release aparece sólo en respuestas estáticas. El Host entrante respeta la lista permitida por Vite.

## Aplicación y reversión

El controlador debe ofrecer snapshot, configuración, aplicación y rollback bajo el mismo flock. Debe guardar la unidad base y todos sus drop-ins efectivos con bytes, dueño, grupo y modo, más configuración gestionada/current y estado operativo. Antes de mutar debe volver a medir y negarse ante cambios desconocidos. Sólo sustituye su propio drop-in/configuración/current; mantiene los archivos preexistentes y no desactiva nginx global.

Debe validar nginx y la unidad antes de intercambiar el servicio que posee5173. El journal durable debe permitir reconocer una transacción incompleta; la reentrada recupera Vite conocido antes de intentar un trabajo nuevo. Fallar la comprobación o el reinicio vuelve al estado previo; un fallo de recuperación queda declarado y no cuenta como éxito. Revertir se hace con un único comando del controlador, que restaura Vite incluyendo los drop-ins realmente instalados. El estado activo no reemplaza la comprobación HTTP y del proceso.

La secuencia productiva concreta y sus comandos se entregan con el CLI validado y el informe de pruebas del PR; no se ejecutan durante la preparación. Antes de activación, Hyde verifica el SHA auditado, snapshot íntegro y restauración ensayada, realiza la medición del Vite actual y registra los resultados. Después mide nginx con el mismo guion; una mejora neutra o regresión se revierte, como exige la constitución. El arnés privado sólo se ejecuta después del veredicto formal de B y de la aprobación de Hyde; en un error antes de `apply` detiene su Vite propio, mientras que un rollback fallido después de intentar `apply` deja la unidad y sus insumos para recuperación comprobada, registrados en `cleanup.json`.
