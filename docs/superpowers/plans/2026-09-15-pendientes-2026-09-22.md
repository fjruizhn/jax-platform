- `api/admin/keys.py`: l.180, 190

Pasos:
1. **Regla nueva.** Todo `except` amplio (`Exception`, `BaseException`, desnudo, o una tupla que incluya alguno de ellos) cuyo cuerpo NO relanza (`raise`) debe llevar `# fail-soft: <razón específica>` en la misma línea del `except`. Es el mismo formato que ya se usa para `except: pass`. Un cuerpo que solo loguea NO exime de la marca: seguir de largo con un log sigue siendo un fail-soft que tiene que decir por qué.
2. **Auditoría, sitio por sitio.** Para cada uno de los 27 se decide y se deja escrito en el reporte:
   - **(a) fail-soft legítimo:** se agrega la marca con una razón concreta, como "el reintento lo hace X" o "un error acá no debe cortar el request del usuario porque Y";
   - **(b) fail-open real:** se arregla, estrechando el tipo de excepción o relanzando, con un test que muestre el comportamiento correcto;
   - **(c) ruido:** el `except` sobra y se quita.
3. El test debe:
   - fallar con un `except Exception: x = None` sin marca (el caso que encontró el review);
   - pasar con la marca;
   - mantener la regla vieja (`except: pass` sin marca).

   Se agregan casos sintéticos puros para cada uno.
4. **Carga.** Si algún arreglo (b) cambia un camino caliente, como `chat.py` o `websocket_hub.py`, se mide.
